# WebRTC Offline Pairing Ideas (Demo)

> ⚠️ **Demo & Technical Prototype**: This project is an experimental proof-of-concept demonstrating how physical and out-of-band transmission channels can establish WebRTC peer-to-peer data channels between nearby devices completely **offline**, with zero centralized signaling servers and without internet connectivity.

---

## 🎯 The Problem

Standard WebRTC enables direct peer-to-peer audio, video, and data transfer. However, WebRTC inherently suffers from a **bootstrap chicken-and-egg dilemma**:

1. Peer A cannot connect to Peer B until they exchange an **SDP Offer** and **SDP Answer** containing session cryptographic keys and network candidates.
2. Standard WebRTC architectures solve this by introducing centralized signaling servers (WebSockets, Firebase, SIP, or decentralized relay swarms).
3. If devices are in an airplane, in a basement, off-grid in nature, or on an isolated local Wi-Fi router without internet access, conventional WebRTC completely breaks down.

---

## 💡 Core Offline Pairing Ideas & Techniques

This project explores and implements several novel techniques to bypass the need for external signaling servers:

### 1. Extreme SDP Compression (~1.5KB down to ~95–110 bytes)

Standard WebRTC SDPs generated by browsers are verbose text blobs (typically 1,500 to 3,000 bytes) filled with repetitive codec definitions and media parameters irrelevant for simple `RTCDataChannel` connections.

To transmit an SDP over bandwidth-constrained physical mediums (like sound tones or small QR codes), we extract only the absolute essential fields:
- **Role**: `O` (Offer) or `A` (Answer)
- **ICE Credentials**: `ufrag` (~4-8 chars) and `pwd` (~22-24 chars)
- **DTLS SHA-256 Fingerprint**: 64 hex characters, compressed to 44 Base64 characters
- **Host Candidate**: Single primary private IPv4 host endpoint (`ip:port`)
- **Session ID**: Random 6-char hex identifier to prevent collision

#### Compact Schema Format:
```text
O|ufrag|pwd|fingerprint_b64|192.168.1.105:54321|sess123
```

On the receiving device, a standards-compliant RFC 8866 SDP document is dynamically reconstructed from this compact string and fed into `setRemoteDescription()`.

---

### 2. Acoustic Signaling with Slotted Leader Election (`ggwave`)

Using sound waves (audible or near-ultrasound ~18kHz–20kHz) allows devices to pair through their built-in speakers and microphones without manual user interaction.

#### The Role Arbitration Problem:
When two people open the app and tap "Pair", neither device knows who should be the **Host** (who creates the Offer) and who should be the **Joiner** (who waits for the Offer and creates the Answer).

#### Slotted Jitter Algorithm:
```
[Device A & B tap Start]
        │
        ▼
Both start listening on microphone
Each device picks a random silence window (e.g. 1.8s – 3.0s)
        │
        ├── Device A's silence timer expires FIRST:
        │     ├── Elected as HOST
        │     └── Broadcasts acoustic Offer tone
        │
        └── Device B detects acoustic Offer tone during its silence window:
              ├── Silence timer cancelled
              ├── Elected as JOINER
              ├── Ingests Offer and generates Answer
              └── Broadcasts acoustic Answer tone back to Host
```

Both devices automatically complete the handshake and establish the WebRTC DataChannel without either user having to decide who is "host" or "client".

---

### 3. Air-Gapped Optical Camera Handshake (Dynamic QR)

For noisy environments or devices without microphones/speakers:
- **Host** generates a high-density, low-ECC QR code containing the serialized compact Offer.
- **Joiner** scans the Host's screen using its camera (`jsQR`).
- **Joiner** instantly computes the compact Answer and presents a return QR code on its screen.
- **Host** scans the Joiner's screen, completing the full cryptographic handshake across air-gapped screens.

---

### 4. Manual Out-of-Band Copy-Paste Fallback

For scenarios where camera or microphone permissions are unavailable:
- Generates a compact base64-encoded URL string.
- Users can copy and paste or send it over local file sharing (AirDrop, Nearby Share, local Bluetooth, or local network messaging).

---

### 5. Serverless Local Subnet ICE Direct-Binding

Once the compact Offer/Answer is exchanged via acoustic, optical, or manual channels:
- The WebRTC `RTCPeerConnection` binds directly to the local subnet host IP addresses (e.g. `192.168.x.x` or `10.x.x.x`).
- Zero STUN or TURN servers are queried.
- Data transfers (end-to-end encrypted chat, latency pings, and chunked binary file transfers) happen entirely over the local peer-to-peer socket.

## 🛠️ Tech Stack

- **Framework**: [Svelte 5](https://svelte.dev/) with Runes (`$state`, `$effect`, `$derived`)
- **Build Tool**: [Vite](https://vite.dev/)
- **Language**: TypeScript (strict mode)
- **Acoustic Engine**: [ggwave](https://github.com/ggerganov/ggwave) (WebAssembly FSK audio data transfer)
- **Optical Scanner**: [jsQR](https://github.com/cozmo/jsQR) & [qrcode](https://github.com/soldair/node-qrcode)
- **Testing**: [Vitest](https://vitest.dev/) & [jsdom](https://github.com/jsdom/jsdom)

## 🚀 Getting Started

### Prerequisites
- Node.js 18+
- pnpm (recommended) or npm

### Installation

```bash
git clone https://github.com/donileong/webrtc-offline-pairing-ideas.git
cd webrtc-offline-pairing-ideas
pnpm install
```

### Local Development Server

Run the development server with local network access enabled so nearby devices on the same Wi-Fi can open the URL:

```bash
pnpm run dev --host
```

Open `http://localhost:5173` or the printed LAN IP (e.g., `http://192.168.x.x:5173`) on two phones, tablets, or laptops.

### Running Tests & Verification

```bash
# Run unit tests
pnpm test

# Type checking & Svelte diagnostics
pnpm check

# Production build
pnpm build
```
